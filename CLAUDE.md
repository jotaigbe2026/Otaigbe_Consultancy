This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Flaney Associates is a static marketing website for a materials engineering consultancy. It is deployed via GitHub Pages at **https://jotaigbe2026.github.io/Flaney_Associates**.

There is no build system, bundler, or package manager. The site is pure HTML/CSS/JS.

The site has four parts:
- `index.html` — the homepage. Hand-written; see **Positioning** below.
- `services/`, `about.html`, `industries.html`, `guides.html`, `featured.html`, `checklist.html`, `contact.html`, `attorney-inquiry.html` — the interior pages, rendered by `generate_pages.py`. **Do not hand-edit them.**
- `content/featured/featured.json` — the month's featured article, rewritten by `generate_featured.py` on a schedule. See **Featured article of the month** below.
- `blog/` — the blog archive imported from the live WordPress site at flaneyassociates.com. Generated by a script; see **Blog** below.
- `publisher/` — an authoring dashboard for writing the monthly post. See **Publishing a monthly post** below.

## Positioning

The site says one thing: *Flaney Associates helps manufacturers and attorneys solve expensive materials, product-performance and manufacturing problems through direct access to senior independent expertise.* Everything else is in service of that.

### Proof discipline

**Every claim on this site must be checkable.** The site previously advertised "200+ Projects Delivered", "50+ Industry Partners", "25+ Years Experience", "Trusted by leaders in aerospace, automotive, energy and biomedical industries" and three testimonials attributing specific dollar figures to unnamed clients. None of it was documented, and for a practice whose main product is an independent opinion that will be tested under cross-examination, an unverifiable claim on the website is a liability rather than an asset.

What replaced it comes from the principal's public record: the degree, the appointments, the fellowships and awards, seven patents and 150+ refereed publications. The homepage says so explicitly, in the section headed *Documented Credentials, Not Claimed Outcomes*.

The rule for anything added later: if it cannot be pointed at — a named award, a published paper, a granted patent, an appointment, or a client quote the client has approved in writing — it does not go on the site. Anonymised case studies are acceptable; invented ones are not.

Two consequences worth knowing:
- **"Free consultation" is gone everywhere.** The CTAs are *Discuss Your Challenge* and, for the lower-commitment path, *Get the Checklist*. A free consultation is what a volume practice offers; this one sells senior attention.
- **Every service links to a page, not to the contact form.** All six "Learn more" links used to be `href="#contact"`, which meant a visitor researching failure analysis was asked to fill in a form before learning anything. That is what `services/` exists to fix.

### Site chrome lives in four places

The navbar and footer markup is duplicated across:

| File | Renders |
|---|---|
| `index.html` | the homepage (transparent navbar over the dark hero) |
| `generate_pages.py` | the twelve interior pages |
| `generate_blog.py` | the blog archive and article pages |
| `publisher/lib/template.js` | the same blog pages, from the browser |

**Changing one means changing all four.** The last two must stay byte-identical — see **The two renderers must agree** below; the parity check will catch a drift between them, but nothing catches a drift between those and the first two except looking.

The Python pair can be re-synced mechanically, which is how the current copies were made: `generate_blog.py`'s `nav()`/`footer()` hold the source of truth, and their literals are spliced into `template.js` with `{up}` → `${up}`. Re-run that rather than hand-editing the template literal.

Five topics, each with children: **How We Help** (the six services), **Industries** (six sectors, anchors on `industries.html`), **Insights** (blog, guides), **About** (bio, credentials, approach, FAQs) and **Contact** (the two intake paths). A persistent *Discuss Your Challenge* button sits at the end.

`initNavDropdowns()` in `lead-capture.js` drives them. It lives there rather than in `script.js` or `blog/blog.js` because every page on the site loads `lead-capture.js` first, so one handler covers the homepage, the interior pages and every blog article. The parent of each menu is a `<button>`, not a link: on a touch device `:hover` latches on the first tap and swallows the second, so the CSS honours either `:hover` or a `.open` class and the button supplies the class.

## Featured article of the month

One archived article is promoted each month into a "Featured this month" band on the homepage and on `guides.html`.

```bash
python3 generate_featured.py                  # write this month's pick
python3 generate_featured.py --dry-run        # print it, write nothing
python3 generate_featured.py --month 2026-11  # preview another month
python3 generate_featured.py --all-months 12  # print the next year's rota
```

Writes `content/featured/featured.json`, overwriting last month's. **It never writes to `blog/`** — every post stays in the archive and the archive page is unchanged. The job only decides which existing article the band points at.

### There is no /content/blog/ of Markdown

Worth stating plainly, because it is the first thing anyone will assume: this site has no `.md` or `.mdx` blog files. The only Markdown in the repository is this file. The blog lives in `blog/data/posts.json`, whose records already carry `title`, `slug`, `categories`, `summary`, `excerpt` and `content` — that file *is* the frontmatter, and it is what `generate_featured.py` reads.

### What is eligible

Four gates, each for a concrete reason:

| Gate | Why |
|---|---|
| not `gated` | A gated post's link goes to a members-only login on flaneyassociates.com — a dead end for a reader arriving cold. |
| `blog/<slug>.html` exists | `posts.json` carries records the site does not render, so the URL is checked against the file rather than assumed. |
| not future-dated | Scheduled posts are committed early and hidden by `hideScheduledCards()` until their morning. Featuring one would publish it ahead of its date and quietly break that contract. |
| on theme, not excluded | At least one category in `CATEGORY_THEMES`, and the slug not in `HOMEPAGE_EXCLUDE`. |

That leaves 16 of 56 posts today.

`HOMEPAGE_EXCLUDE` is **imported from `generate_blog.py`**, not copied — it already encodes which posts belong in the archive but not on the front of the site, and two copies would drift.

`CATEGORY_THEMES` maps each category to the service areas it speaks to. It is both the relevance filter and the source of the `summary` text, so the reason a post was chosen is always the reason printed in the JSON — the two cannot disagree.

`THEME_OVERRIDE` names two posts whose categories understate them. *Bridging Science and Law* and *From Lab to Courtroom* carry only **Board Room Governance**, but they are squarely about materials-science expertise in litigation, which is a core service. They are named individually rather than admitting the whole category, which would also let the boardroom-AI posts back in.

### Why the pick is deterministic rather than random

The brief said "randomly select". A literal `random.choice()` breaks in CI: a retried job, a manual dispatch or a local preview would each pick a different article, and you could not reproduce what shipped.

`choose()` uses **rendezvous hashing** — every candidate is hashed with the month and the lowest `sha256(month|slug)` wins. It looks arbitrary month to month, and:

- Re-running any month reproduces the same article.
- Adding a post only changes a month's pick if that new post happens to win it. This matters because the publisher adds a post most months, so the pool grows between runs; `hash(month) % len(pool)` would reshuffle every month instead.

There is **one look-back**: the previous month's winner is excluded. Independent draws collide, and with 16 candidates August and September landed on the same article — which reads as broken rather than random. The excluded slug is recomputed, not remembered, so this stays reproducible. Wider-spaced repeats are left alone; they are the accepted cost of not keeping a state file. Run `--all-months 12` to see them coming.

The output carries **no wall-clock timestamp** on purpose. It is a pure function of `(month, posts.json)`, so a re-run inside the same month produces a byte-identical file and the workflow's "nothing to commit" check actually works.

### highlight_excerpt

Capped at 40 words, cut on a word boundary. It comes from the **first real body paragraph**, not from `summary` or `excerpt`, both of which are unreliable here:

- `summary` is built by `summarise()`, which does not strip section headings — a post opening with one reads *"A New Era in Construction The buildings we live and work in…"*, a heading welded to a sentence.
- Several WordPress excerpts carry shortcodes, repeat the title, or describe a different article entirely.

Two things the paragraph walker has to handle, both found by testing every eligible post:

- **The title is often repeated at the top**, sometimes as its own paragraph and sometimes with the body running on from it inside the same `<p>`. The prefix is *stripped*, not the paragraph discarded — discarding it threw away a 317-word body and left the contact-details footer as the excerpt.
- **Every article ends with the same contact block and byline.** They are prose in a `<p>` with nothing structural marking them as not-the-article, so `BOILERPLATE` filters them by wording.

Titles arrive entity-encoded from the WordPress API (`Pglass &#038; PET`) and are decoded before going into JSON — JSON has no HTML context, so whatever renders the file would otherwise show the raw entity.

### Where it appears

**`featured.html` is the page.** It has a stable URL that can be linked from a newsletter or a LinkedIn post, and it is listed under **Insights** in the nav and under **Company** in the footer.

It exists because the band alone was not findable: on the homepage it sits about 6,800px down — nine screens, two thirds of the page — inside `#blog`, and nothing linked to it. The band's "Featured this month" label is now a link into the page, on both the homepage and `guides.html`.

`featured.js` fills in `#featuredBand` from the JSON, on all three pages. The path comes from `data-src` on the element rather than being hardcoded, so a page at a different depth can carry one.

**`featured.html` also carries `#featuredEmpty`.** Hiding everything works on the homepage, where the section simply vanishes; on a dedicated page it would leave a blank page under a heading promising an article, so that block is shown instead. Pages without one hide, as before.

**The band ships with `hidden` and is revealed only once real content is in it.** Every failure mode is therefore identical: no band at all, and the page reads as though the section was never there. That covers the month before the first run, a file not yet committed, a fetch blocked on a `file://` URL, and malformed JSON. A half-rendered card with an empty heading would be worse than nothing on a page whose whole argument is that this practice is careful.

On the homepage the band sits **outside** the `<!-- BEGIN imported-blog -->` markers — `generate_blog.py` replaces everything between them.

### The monthly workflow

`.github/workflows/featured.yml` runs at 06:00 UTC on the 1st, and on demand from the Actions tab (with optional `month` and `dry_run` inputs). It holds `permissions: contents: write`, stages **only** `content/featured/featured.json` — never `git add -A`, which would sweep up anything else in the tree — and skips the commit when the file is unchanged.

**It runs on the default branch.** Nothing happens until this work is merged to `main`.

Adding the band's CSS to `styles.css` re-stamped the `styles.css?v=` URL in all 21 blog pages — one line each, no article text. That is a site-build consequence of editing the stylesheet, not something the monthly job does; the job only ever writes the one JSON file.

```bash

This is required (rather than opening index.html directly) because the gated PDF download system and the publisher both use `fetch()`, which is blocked by browsers on `file://` URLs.

To rebuild everything the generators own:

```bash
python3 generate_pages.py          # services/, about, industries, guides, checklist, contact, attorney
python3 generate_blog.py           # blog archive, article pages, the homepage insights strip
python3 generate_checklist_pdf.py  # the lead-magnet PDF

All three are idempotent and independent of each other. ## Publishing a monthly post

`publisher/` is a static dashboard for composing one post a month. Nothing about it is privileged — it is the same HTML/CSS/JS as the rest of the site, and it runs entirely in the browser. It cannot write to the repository, so it hands back every file a publish touches and you commit them.

1. Open `http://localhost:8000/publisher/`.
2. **Start next month's post** fills in the date, author and categories from the monthly template. The date is the first month not already taken by a post, so several months can be queued in one sitting.
3. Paste the article, pick categories, drop in a featured image.
4. **Generate the publish bundle** produces six files, downloadable individually or as one zip:

| File | |
|---|---|
| `blog/<slug>.html` | the new article page |
| `blog/images/<slug>.<ext>` | the featured image |
| `articles/<slug>.pdf` | the gated download |
| `blog/data/posts.json` | replaced, with the new post merged in |
| `blog/index.html` | replaced — the archive, regenerated |
| `index.html` | replaced — the homepage "latest posts" strip |

5. Unzip over the repository root and commit. Running `python3 generate_blog.py` afterwards is optional and produces no diff.

### Editing a published post
The **Edit published** tab in step 2 lists the 19 posts whose body actually lives on this site (gated posts are excluded — their text has never been here, so an edit would look like it silently failed). Choosing one loads it back into the form; **Generate** then rebuilds the same files with `replace` status rather than creating new ones.

Three deliberate constraints:

- **The slug is locked.** Changing a live URL breaks every LinkedIn post and search result pointing at it, and strands the old page — the bundle has no way to delete a file.
- **The date is locked.** A correction is not a republication, so a typo fix does not get promoted to the top of the archive and the homepage.
- **The PDF is rebuilt** from the edited text, so a reader can never download a PDF contradicting the corrected page.

Two things make this work, and both are easy to break:

**The body is loaded from the rendered page, not from `posts.json`.** `posts.json` holds the *raw* WordPress markup — shortcodes, editor attributes, the lot — and `clean()` is applied by `generate_blog.py` at render time. Loading that raw source would show markup the author never wrote. `loadBody()` therefore fetches `blog/<slug>.html` and takes `.article-body`'s innerHTML, which is the authoritative cleaned text.

**`build_post()` skips `clean()` for `local`/`edited` posts.** `clean()` is *not* idempotent: `promote_pseudo_headings()` promotes bold runs the previous pass left alone, so a second pass keeps changing the text (measured: only 5 of 19 rendered bodies survive a second `clean()` unchanged). Since the publisher stores already-clean content, re-cleaning would rewrite the article on every regeneration. Both renderers now use an edited body verbatim, which is what makes their output byte-identical — verified by SHA-256 on a real edit.

A consequence worth knowing: `template.js`'s `article()` renders `content` verbatim and so is only correct for `local`/`edited` posts. That is all it is ever asked to do — the bundle writes exactly one article page, the post being created or edited — but do not reuse it to render an imported post.

### Images are optimised on upload
`optimiseImage()` in publisher.js downscales to 1600px wide and re-encodes before the image ever reaches a bundle. The article renders its hero in a 760px column, so anything wider buys nothing on screen; 1600 keeps it sharp at 2x on a retina display.

Photographs saved as PNG are the case that matters — the first image published through the dashboard was a 1.8 MB PNG, more than three times the size of anything else on the blog. Re-encoded it is 138 KB.

Two guards: a PNG that actually uses transparency stays a PNG, because JPEG cannot represent an alpha channel; and if re-encoding produces something *larger* (a small flat graphic, or an already-optimised file) the original is kept untouched. Animated GIFs are skipped entirely, since a canvas round-trip would flatten them to the first frame.

The chosen format decides the stored filename, so a converted photo becomes `<slug>.jpg` — which also means a format change naturally busts any cached copy of the old image.

### Deleting a published post
Edit mode has a **Delete this post** button. Neither a zip nor a folder write can express "remove this file", so the delete arrives as a manifest (`.publish-delete`) listing the paths to remove; `publish.sh` applies it, then **re-runs `generate_blog.py`** — necessary because other articles carry *Related articles* cards pointing at the deleted post, and skipping the rebuild would leave links to a 404 scattered across the site.

The manifest is a plain text file that causes unprompted deletion, so `publish.sh` only honours paths under `blog/` or `articles/` and rejects anything containing `..`. Verified against a manifest listing `/etc/hosts`, `../outside/victim.txt` and a repo-root file: all three refused, the legitimate paths removed.

### Getting a bundle into the repo

**The short version: press Generate, then run `./publish.sh`.**

`publish.sh` does its own `cd` to the repository, because Terminal opens in the home folder and running git there is the single most common way to get nowhere. It unpacks a downloaded bundle if one is waiting, derives the commit message from the most recently modified post in `posts.json` (`Publish:` when the article file is new to git, `Update:` when it already exists, and plain `Site update` when no post changed at all), commits, pushes and prints the live URL.

There are two ways to get files into the repo:

**Direct folder write (Chrome/Edge).** `showDirectoryPicker()` grants the page write access to one folder. The handle is kept in IndexedDB — it is a live object, not a path, so it cannot go in `localStorage` — and needs re-approval after a browser restart, which is why a stored handle counts as connected only once `queryPermission` actually returns `granted`. The picked folder is rejected unless it contains `index.html`, `blog/` and `publisher/`; writing five files into the wrong folder is an easy mistake to make in a picker.

**The zip (any browser, and the Safari fallback).** Note that **double-clicking a zip in Finder does not work** — macOS expands it into a new folder rather than merging it into the repo, so the files land somewhere harmless and the publish silently does nothing. `publish.sh` and the generated command both use `unzip -o`, which merges. The newest matching zip is chosen (`ls -t | head -1`), because a second download of the same post arrives as `flaney-<slug>-1.zip` and unpacking the older one would republish stale content.

The repository path used by the generated command lives in `localStorage` under `flaney_publisher_paths`, **not** in `template.json` — that file is committed and served publicly, and a local path containing the machine's username does not belong in it.

### Getting a bundle into the repo (detail)
The Files tab prints one command that unzips the bundle, commits and pushes. **Double-clicking the zip in Finder does not work** — macOS extracts it into a new folder rather than merging it into the repo, so the files land in the wrong place. `unzip -o` merges and overwrites without prompting.

The command picks the newest matching download (`ls -t | head -1`) because a second download of the same post arrives as `flaney-<slug>-1.zip`, and unzipping the older one would quietly publish a stale bundle.

The repository path it needs lives in `localStorage` under `flaney_publisher_paths`, **not** in `template.json` — that file is committed and served publicly, and a local filesystem path (with the machine's username in it) does not belong there. The field is in step 1; without it the command shows a placeholder.

### The monthly template
Defaults live in **`publisher/template.json`**, committed to the repo:

| Field | Current setting | |
|---|---|---|
| `titlePattern` | `""` (empty) | Deliberate — a fresh headline is written each month. Every one of the 55 archived titles is an editorial headline, and dated ones perform worse when shared. A non-empty pattern supports `{month}`, `{year}`, `{month_short}`, `{n}`. |
| `author` | `Joshua Otaigbe` | The July 2026 post moved to a named byline; the rest of the archive is `Editorial Team`. |
| `publishDay` | `15` | The 14th and 15th account for 12 of 55 posts — more than any other date. |
| `categories` | `Advanced Materials Engineering` | The most-used category, on 35 of 55 posts. |
| `byline` | name + role credential | Signed at the end of every post, above the PDF box. Wrapped in `<p><em>…</em></p>` — **an inline tag, never a class**, because `clean()` strips `class` attributes and any styling done that way would vanish on the first regeneration. `<em>` survives `clean()` intact and round-trips unchanged. `toBlocks()` carries the italics into the PDF too. The older key name `closing` is still read as a fallback so a per-device override saved before the rename still loads. |

`localStorage` (`flaney_publisher_template`) holds a **per-device override** that wins over the file; the status line in the panel header says which is in effect. *Save for this browser* writes the override, *Download for repo* writes `template.json` back out so a change can be committed and picked up everywhere. The file is optional — the dashboard falls back to `localStorage` alone if it is missing.

An empty `titlePattern` is treated as a setting, not as missing data: **Start next month's post** fills in everything else and puts the cursor in the title field.

### publisher/ is served publicly
Pages serves the whole repository, so the dashboard is live at `/Flaney_Associates/publisher/`. Reviewed and accepted (August 2026): it reads only files that are already public (`posts.json`, `index.html`, `template.json`), writes nothing anywhere, holds no credentials, and carries `noindex` so it stays out of search results. Keeping it deployed is what lets it be used from any machine without cloning the repo or running a local server.

### Why the bundle includes regenerated pages
A new article page on its own would never be linked from anywhere. The archive and the homepage strip both list every post, so both have to be rebuilt on every publish — which is exactly what `generate_blog.py` does. The publisher reproduces that work in the browser so a post can ship without running Python.

### The two renderers must agree
`publisher/lib/template.js` is a port of `generate_blog.py`'s `card()`, `build_post()`, `build_index()` and `update_homepage()`. Both write the same files, so if they drift, regenerating silently rewrites pages the publisher made. **They currently produce byte-identical output, and changing one means changing the other.** Two things keep it that way:

- `summarise()` is not reimplemented. Every post carries a stored `summary` in posts.json and both renderers just read it — see **Summaries** below.
- `parseBody()` applies the same `[ \t]{2,}` → single-space collapse that `clean()` does, so the stored body matches what Python would write.

To check parity after a change, render the same post both ways and compare. `template.js` is a browser file, so under Node it needs `window` and a stub for the one DOM call it makes — `decode()` round-trips entities through a `<textarea>`. Load it with `new Function(source)()`, stub `document.createElement` to return an object whose `innerHTML` setter unescapes entities and whose `value` getter returns the result, then compare `T.homepage()`, `T.archive()` and `T.article()` against what `generate_blog.py` wrote to disk. Note that `readAssetVersions()` in publisher.js supplies the whole `?v=...` suffix, not the bare hash — passing a bare hash produces a spurious diff on the stylesheet link.

`article()` is only correct for `local`/`edited` posts, so compare the one post carrying `local: true`.

### The PDF
`publisher/lib/pdf.js` writes the PDF by hand — the page is static, so there is no server and no library to lean on. It uses only the base-14 Helvetica faces, so nothing needs embedding. Layout mirrors `generate_pdfs_v2.py`: Letter, navy headings, 11/17 justified body, blue bullets, contact block, page footers.

A word is a list of styled *segments* rather than a string, because a style can change mid-word: `<strong>…to ask</strong>.` is one word ending in a bold run and a regular full stop. Treating each run as its own word puts a space before the period.

`publisher/lib/zip.js` writes STORED (uncompressed) zip entries. Everything in a bundle is either already compressed or tiny, so DEFLATE would buy nothing.

## Blog

`blog/` holds the archive imported from the live WordPress site. **Do not hand-edit the generated HTML** — change the scripts and regenerate.

| Script | Purpose |
|---|---|
| `extract_blog.py` | Pulls posts + featured images from the flaneyassociates.com REST API into `blog/data/posts.json` and `blog/images/` |
| `generate_blog.py` | Renders `blog/index.html`, one `blog/<slug>.html` per full-text post, and the "latest posts" strip on the homepage |

```bash
python3 extract_blog.py     # refresh content from the live site (needs curl)
python3 generate_blog.py    # rebuild all blog HTML
```

`generate_blog.py` is idempotent — running it repeatedly is safe.

### Locally authored posts
Posts written in `publisher/` live only in `posts.json` and are flagged `local: true`. `extract_blog.py` rewrites that file from the WordPress API, so it deliberately carries local posts across (`local_posts()`); without that, a content refresh would delete them. They also carry `pdf: "articles/<slug>.pdf"`, which is what puts the gated download block on the article page.

### Summaries
Every post carries a stored `summary`. `summarise()` returns it verbatim when present and only derives one from the body as a fallback. This exists because the publisher renders the archive, the homepage strip and the article page in JavaScript: re-deriving a summary from the body in two languages is the one thing guaranteed to drift, and a drifting summary means the card and the `<meta description>` disagree depending on which renderer ran last. For a post written in `publisher/`, `summary` is whatever the author typed in the **Card summary** field.

### Scheduling
Every card and article page carries `data-publish="YYYY-MM-DD"`. `hideScheduledCards()` in `lead-capture.js` hides any card dated ahead of today, and `blog.js` drops those cards from the archive's search, category filters and every count — the hero total, the subtitle, the chip badges and the results line. A scheduled post is committed like any other and simply appears on its own on the right morning; no rebuild, no deploy.

The article page itself stays reachable at its URL so it can be proofed, and `blog.js` puts a "Scheduled preview" banner on it until the date passes.

**Scheduling is presentation, not embargo.** A scheduled post's full text sits in `blog/data/posts.json` and at `blog/<slug>.html` from the moment it is committed, and both are publicly readable — Pages serves a static site, so there is no server that could withhold them. The hiding happens in the visitor's browser. Reviewed and accepted (August 2026): it is what buys the auto-appear behaviour and the ability to proof the real page early, and these are engineering articles rather than embargoed results. **If a post ever genuinely needs an embargo, do not commit it until the day** — no amount of client-side hiding will give you one.

### Gated posts
36 of the 55 source posts sit behind the Simple Membership plugin on flaneyassociates.com; the API returns a login stub instead of a body. Those are flagged `gated: true` and appear on the archive as cards with their real title, date, categories, image and published abstract, badged **Members only** and linking to the source site. **No body text is ever invented for them.** Only the 19 public posts get their own page.

### Content cleaning (`generate_blog.py`)
The source HTML arrives with editor artifacts, handled by `clean()`:
- literal `[vc_*]` / `[wpb_*]` shortcodes are stripped (WordPress renders these server-side, the API does not)
- Gutenberg block delimiters (`<!-- wp:paragraph -->`) are stripped — some posts use blocks rather than WPBakery
- inline `style`/`class`/`id` attributes and wrapper `<div>`s are removed
- `promote_pseudo_headings()` turns bold runs that act as section headings into real `<h3>`s — deliberately conservative, so inline emphasis is left alone
- `drop_leading_title()` removes the title from the top of the body; most posts repeat it, and the page already renders it as the `<h1>`
- `balance_inline_tags()` drops close tags orphaned by heading promotion
- tables are wrapped in `.table-scroll` so wide content scrolls itself, never the page

Titles arrive entity-encoded (`Pglass &#038; PET`), so anything comparing or indexing them must decode first — see `_norm()` and `attr()`.

### Search index
`search_key()` folds curly quotes and dashes to ASCII when writing each card's `data-title`; `blog.js` folds the query the same way. Without this, searching `didn't` misses `didn’t`. Keep the two tables in sync.

### Cache busting
`asset_version()` appends a content hash to `blog.css` / `blog.js` URLs. Without it, returning visitors get new markup with a stale stylesheet or an old search script after a deploy.

`summarise()` builds card and meta descriptions **from the article body**, not the WordPress excerpt: several source excerpts carry shortcodes, repeat the title, or describe a different article entirely. Gated posts have no body, so their published abstract is used once cleaned.

### Homepage integration
`update_homepage()` injects a "Latest from the Flaney Associates blog" strip into the `#blog` section of `index.html`, between the `<!-- BEGIN imported-blog -->` / `<!-- END imported-blog -->` markers. Regenerating replaces only the marked block.

**Not every post is featured.** `HOMEPAGE_EXCLUDE` names the ones kept off it. The blog covers materials engineering, board governance and general-interest science, and all three belong in the archive — but the homepage has one job, which is to tell a visitor with an expensive materials problem that they are in the right place, and a wellness article or a general boardroom-AI piece in that strip works against it. New posts are featured by default; the list names the exceptions, and it must stay in step with `HOMEPAGE_EXCLUDE` in `publisher/lib/template.js`.

The twelve hand-written sector briefings that used to sit below the strip under a "Sector briefings" heading now live on `guides.html`, and the generated block no longer emits that heading.

### Styling
`blog/blog.css` layers on top of `styles.css` and reuses its custom properties. It also defines `.navbar-solid`, because `styles.css` only makes the navbar readable once `.scrolled` is applied — article pages open on a white background and need it from load. `blog/blog.js` handles archive search/filtering plus the nav toggle and scroll state (blog pages do not load the site-wide `script.js`).

## Architecture

### Homepage (`index.html`)
Hand-written, and the only page `generate_pages.py` does not own. Sections in order: `#navbar → #hero → #problem → #services → #why → #process → #credentials → #industries → #blog → #checklist → #contact → footer → #downloadModal`.

`#blog` carries the `<!-- BEGIN imported-blog -->` markers that `generate_blog.py` rewrites; everything else in the file is edited by hand. The old `.trust-bar`, `#expertise`, `#about` and `#testimonials` sections are gone — see **Proof discipline** above for why.

### Lead Capture System (`lead-capture.js`)
Email validation, the Formsubmit bridge and the gated PDF modal live in `lead-capture.js`, which **every page loads first** — the homepage before `script.js`, blog pages before `blog/blog.js`. It used to sit inside `script.js`, but blog pages never load that file and blog posts now carry their own gated download; one copy beats two that drift. Everything in it is null-guarded, so a page with no modal or no `.gated-download` button is a no-op.

It also holds `initNavDropdowns()`, for the same reason — see **Navigation** above.

Two lead capture paths both funnel to `sendToFormsubmit(data, subject, to)`, where `to` is a key into `LEAD_INBOXES` (see **Two inboxes** above) and defaults to the general address:
- **Enquiry forms** (`#contactForm`, wired in `script.js`) — one handler serves the homepage, `contact.html` and `attorney-inquiry.html`, reading `data-inbox` and `data-subject` off the `<form>` and picking up whichever named fields the page actually carries.
- **PDF download modal** (`#downloadModal`) — gated downloads; captures name/email/company and the article title before triggering the download. The modal markup is identical on every page, so `index.html`, `generate_pages.py`'s `download_modal()`, `generate_blog.py`'s `download_modal()` and `template.js`'s `downloadModal()` must stay in step. Per-download wording is handled with `data-modal-*` attributes rather than by editing that markup — see **The lead magnet** above.

Captured lead data is persisted in `localStorage` under the key `flaney_lead`. On subsequent visits, returning leads bypass the modal and download PDFs directly.

Email validation (`validateEmail()`) blocks disposable domains (hardcoded list at top of `lead-capture.js`) and runs on both forms with 400ms debounce + immediate blur validation.

### Styling (`styles.css`)
CSS custom properties defined in `:root` control the entire colour palette and spacing. Primary brand colours: `--primary: #1a3a5c` (navy), `--accent: #2d8cf0` (blue). Responsive breakpoints at 768px and 480px.

Scroll-triggered fade-in animations are applied via `IntersectionObserver` in `nav.js` to `.service-card`, `.expertise-card`, `.industry-card`, `.process-step`, `.blog-card`, `.problem-card`, `.cred-card` and `.audience-card`. The observer sets the starting `opacity: 0` itself, so a page whose JavaScript fails to load still shows its content.

`.btn-outline` defaults to the **light**-surface treatment (navy text, grey border). It used to be white-on-transparent, because the only place it appeared was the dark hero; it now appears on white cards far more often, where white text on a white card is an invisible button — which is exactly what happened to the attorney CTA. Dark containers opt back in through the `.hero, .cta-section, .cta-band, .magnet, .aside-dark` selector list. **Add any new dark container to that list.**

### Article Generation Scripts
`generate_checklist_pdf.py` is separate from these and writes the lead magnet — see **The lead magnet** above.

All three Python scripts share the same brand colour constants (`PRIMARY`, `ACCENT`, etc.) and helper pattern. Each article is a standalone function that receives `story` (reportlab) or `doc` (python-docx) and appends content. A shared `add_contact_footer()` / `footer_block()` is appended to every article.

When adding a new article:
1. Add an article function to the relevant Python script.
2. Register it in the `articles` list in `if __name__ == "__main__"`.
3. Add an entry to `BRIEFINGS` in `generate_pages.py` and re-run it. That renders the card on `guides.html` with the `data-pdf` and `data-title` attributes the download gate needs. Briefings no longer appear on the homepage.
